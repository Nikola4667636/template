# Trip Service (TripGo) — Лабораторные работы 1–2

Сервис управления жизненным циклом поездок для платформы такси TripGo.

На этапе лабораторных работ 1–2 реализованы создание, получение и завершение
поездки, а также `/health` и `/ready`. `make generate` генерирует API только для
этих операций. Таблица `trip_positions`, операции с позициями и поле
`last_position_at` добавляются в лабораторной работе 3.

## Требования

- Go 1.27.0 или новее;
- GNU Make и `golangci-lint` v2, совместимый с используемой версией Go;
- Docker с запущенным daemon и установленный `tripgoctl` для учебного окружения.

`oapi-codegen`, Goose и `mockgen` закреплены в `go.mod` и запускаются через
`go tool`; отдельно устанавливать их не требуется. При первом запуске нужен
доступ к загрузке зависимостей Go.

### 1. Поднятие инфраструктуры

```
tripgoctl cluster start       # если кластер еще не запущен
tripgoctl environment start   # поднять PostgreSQL и сгенерировать .env
```

После генерации `.env` добавьте отсутствующие настройки из `.env.example`.
В частности, генератор окружения может не добавлять HTTP-таймауты сервиса:

```dotenv
HTTP_READ_TIMEOUT=5s
HTTP_READ_HEADER_TIMEOUT=2s
HTTP_WRITE_TIMEOUT=10s
HTTP_IDLE_TIMEOUT=120s
```

Адреса БД и коллектора берутся из сгенерированного `.env`.
### 2. Применение миграций
```
make migrate
```
### 3. Запуск сервиса
```
make run
```
Сервис поднимется на порту, указанном в .env (по умолчанию http://localhost:8080).

## Принятые решения и архитектура

Доменная модель и её правила находятся в `internal/domain/trip`. Отдельного
`internal/model` пока нет: usecase и репозитории обмениваются доменной поездкой,
а структуры HTTP-контракта остаются в `internal/generated`. Дополнительный пакет
сейчас дублировал бы те же поля без отдельной ответственности.

### 1. Уровень изоляции транзакций по умолчанию
Для TxManager выбран уровень изоляции Read Committed.
Почему: Для операций создания поездки и записи в журнал статусов этого уровня достаточно в сочетании со строгими ограничениями схемы PostgreSQL (уникальный индекс). Это обеспечивает высокую производительность пула соединений без избыточного оверхеда Serializable.

### 2. Менеджер транзакций (TxManager)
Реализован интерфейс TxManager с методом Do(ctx, fn).
Объект транзакции pgx.Tx внедряется непосредственно в context.Context.
Репозиторий прозрачно проверяет наличие активной транзакции в контексте: если она есть, запросы выполняются внутри неё; если нет — напрямую через pgxpool.Pool.
Вложенные вызовы Do переиспользуют существующую транзакцию из контекста без открытия новой.
При ошибке или панике внутри fn происходит автоматический ROLLBACK, гарантирующий атомарность записи в таблицы trips и trip_status_history.

### 3. Запрет двух активных поездок у одного водителя
Ограничение реализовано на уровне базы данных с помощью уникального частичного индекса (Partial Unique Index) в PostgreSQL:

CREATE UNIQUE INDEX idx_trips_driver_active 
ON trips (driver_id) 
WHERE status = 'active';

При попытке создания второй активной поездки PostgreSQL возвращает ошибку 23505 (unique_violation). Сервис перехватывает её на уровне репозитория и трансформирует в доменную ошибку driver_busy (409 Conflict в HTTP API). Это гарантирует строгую защиту от race condition при параллельных запросах.


### 4. Сценарии поездок

Создание, получение и завершение поездки находятся в отдельных пакетах
`internal/usecase/trip/create`, `get` и `finish`. Каждый сценарий объявляет
интерфейсы своих зависимостей в `contract.go`. Контейнер создаёт репозиторий,
менеджер транзакций и сценарии, затем передаёт их HTTP-хендлеру.

Создание проверяет доменные параметры и сохраняет поездку вместе с начальной
историей статуса в одной транзакции. Завершение читает поездку через
`SELECT ... FOR UPDATE`, вызывает доменный `Trip.Finish` и сохраняет состояние
вместе с историей в той же транзакции. Время передаётся сценариям зависимостью:
в приложении используется `time.Now`, в тестах — фиксированная дата.

Unit-тесты сценариев используют моки репозитория и менеджера транзакций,
сгенерированные `mockgen`. `make test` запускает тесты с `-race -count=2` и
печатает покрытие по пакетам и общий итог. Профиль сохраняется в `coverage.out`.

### 5. HTTP-слой

Хендлеры поездок находятся в `internal/http/trip/create`, `get` и `finish`.
Каждый пакет объявляет интерфейс своего usecase в `contract.go`; моки
генерируются рядом с тестами. Общий перевод доменной поездки в ответ OpenAPI
находится в `internal/http/trip/convert.go`, чтобы три хендлера использовали
одинаковый формат ответа. `health` и `ready` выделены в отдельные пакеты.

`internal/http/router.go` связывает хендлеры через адаптер с интерфейсом
сгенерированного API. UUID пути и заголовка разбирает сгенерированный роутер.
Сервер в `internal/http/server.go` получает готовый `http.Handler`, настраивает
таймауты, запуск и graceful shutdown. Контейнер создаёт все зависимости.
Транспорт работает с usecase через интерфейсы и не импортирует репозиторий
или реализацию подключения к БД. Для readiness объявлен интерфейс `pinger`.

Маппинг доменных ошибок в HTTP-статус и `Problem` собран в
`internal/http/domainerror`. Обёрнутые ошибки распознаются через `errors.Is`
и `errors.As`; клиент получает поле и причину ошибки валидации. Неожиданные
ошибки отвечают `500 internal_error`, подробности один раз попадают в лог.
Логгер передаётся HTTP-хендлерам зависимостью.

JSON создания ограничен 1 МиБ; неизвестные поля, несколько объектов и
отсутствующие обязательные поля, включая вложенные координаты, дают 400.
Нулевые цена и координаты допустимы. Ошибки маршрутизации возвращаются в формате
`application/problem+json`. При панике до начала ответа middleware также отдаёт
`500 internal_error` в этом формате. Если заголовки уже отправлены, изменить
статус нельзя: паника логируется со стектрейсом, соединение прерывается.

### 6. Репозиторий и инфраструктура PostgreSQL

Пул подключения находится в `internal/infra/postgres`, менеджер транзакций —
в `internal/infra/postgres/transaction`. Контейнер создаёт их и передаёт пул
репозиторию `internal/repository/trip`.

В репозитории `repo.go` содержит конструктор и общие методы, `save.go` —
создание и обновление поездки, `fetch.go` — чтение, `history.go` — запись
истории статусов, `convert.go` — преобразование строки БД в доменную поездку.
В `contract.go` объявлен узкий неэкспортируемый интерфейс SQL-исполнителя:
только `Exec` и `QueryRow`. Ему соответствуют и пул, и транзакция pgx.

Все запросы параметризованы и ограничены `DATABASE_QUERY_TIMEOUT`.
Если в контексте есть транзакция, репозиторий выполняет запросы через неё;
иначе использует переданный пул. Создание поездки с историей и завершение
поездки с историей остаются атомарными операциями.

### 7. Телеметрия и остановка

`internal/infra/telemetry` создаёт JSON-логгер и OTel SDK: ресурс, пакетный
экспорт трейсов и периодический экспорт метрик по OTLP. Поддерживаются
HTTP/protobuf и gRPC. HTTP-экспорт дописывает к базовому адресу `/v1/traces`
и `/v1/metrics`. Остальные стандартные настройки экспортёров читает SDK;
их семантика описана в [документации OpenTelemetry](https://opentelemetry.io/docs/languages/sdk-configuration/otlp-exporter/).

Ресурс содержит `service.name`, `service.version`, `service.namespace` и
`deployment.environment`. Версия берётся из информации о сборке, для локальной
сборки — `dev`; её можно переопределить через `service.version` в
`OTEL_RESOURCE_ATTRIBUTES`. Неизвестный протокол или сэмплер, некорректный URL,
уровень лога и размер пула отвергаются при запуске.

Контейнер передаёт логгер, tracer provider и meter provider зависимостями.
В бизнес-коде нет глобального логгера или обращений к глобальным провайдерам.
В `main` остаётся только отдельный JSON-логгер для фатальной диагностики,
когда конфигурация или контейнер ещё не созданы. Ошибки фонового экспорта SDK
попадают в структурированный лог уровня `Warn`; HTTP продолжает работать.

Логгер добавляет `trace_id` и `span_id` из контекста; вне спана поля пустые.
Middleware пишет одну запись `request handled` после подготовки ответа:
метод, шаблон маршрута, статус и длительность. У `2xx` и `4xx` уровень `Info`,
у `5xx` — `Error`. Подробности внутренней ошибки включаются в эту же запись.
Тела запросов и ответов не логируются. Неизвестный маршрут получает постоянную
метку `/unmatched`, поэтому пользовательский URL не создаёт новые серии.

Порядок обёрток: `Recover → Tracing → Logging → Metrics → роутер`.
Трейс HTTP создаётся через `otelhttp` с W3C TraceContext; его имя содержит метод
и шаблон маршрута. `requeststate` хранит результат обработки и завершающие
действия: паника до начала ответа учитывается как `500`, после начала ответа
сохраняется уже отправленный HTTP-статус. Паника всегда попадает в лог уровня
`Error`; её спан получает `codes.Error`, `error.type` и исключение.
Автоматические HTTP-метрики `otelhttp` выключены: отдельный middleware
записывает требуемые метрики после восстановления ошибки без дублирования.

Пул получает tracer на базе `otelpgx`. Дополнение в `infra/postgres` проставляет
`db.operation.name`, `db.collection.name` и записывает гистограмму с `error.type`
(SQLSTATE для ошибок PostgreSQL, пустая строка для успеха). В телеметрии нет
текста SQL, параметров запросов и реквизитов подключения. Имена таблиц для
меток ограничены таблицами текущей лабораторной. Подготовка SQL-выражений
также может создавать дочерние спаны.

Наблюдатели `ObserveCreate` и `ObserveFinish` оборачивают usecase в контейнере.
После успешного возврата, когда транзакция уже зафиксирована, они увеличивают
счётчики и пишут `trip created` / `trip completed` с ID поездки. При ошибке
событие и счётчик не появляются. Домен и usecase не импортируют OTel.
Gauge активных поездок вызывает `CountActive` при сборе метрик и отражает
реальное состояние PostgreSQL, включая данные до перезапуска процесса.

При сигнале контейнер создаёт один контекст с бюджетом `SHUTDOWN_TIMEOUT`:
HTTP перестаёт принимать запросы и дожидается текущих → SDK отправляет
оставшиеся метрики и спаны → закрывается пул БД. Во время финального сбора
gauge пул ещё доступен. По истечении общего бюджета HTTP-соединения закрываются
принудительно, сервис пишет ошибку и завершает процесс.

## Проверка observability

```bash
make generate
make lint
make test
make test-integration
make migrate
make run
# В другом терминале: адреса Jaeger, Grafana и Prometheus.
tripgoctl connect
```

Создайте, получите и завершите поездку. Возьмите `trace_id` из JSON-лога и
найдите его в Jaeger: под HTTP должны быть SQL-спаны. Для метрик дождитесь
интервала экспорта SDK и следующего сбора Prometheus.

Необязательный шаблон дашборда Grafana находится в
`deploy/grafana/trip-service.json`. Он хранится для воспроизведения графиков
в новом окружении; Go-сервис его не читает и автоматически не импортирует.
Импорт выполняется вручную через Dashboards → New → Import; используется
источник данных учебного окружения с UID `prometheus`.
Дашборд показывает все шесть метрик;
p95 на нём рассчитывается по накопленной гистограмме с момента запуска
процесса, что отражено в заголовках панелей.

| OTel | Имя после преобразования в Prometheus |
|---|---|
| `http.server.request.duration` | `http_server_request_duration_seconds_{bucket,sum,count}` |
| `http.server.active_requests` | `http_server_active_requests` |
| `db.client.operation.duration` | `db_client_operation_duration_seconds_{bucket,sum,count}` |
| `tripgo.trips.created` | `tripgo_trips_created_total` |
| `tripgo.trips.completed` | `tripgo_trips_completed_total` |
| `tripgo.trips.active` | `tripgo_trips_active` |

Для сдачи приложите в описание PR скриншот трейса Jaeger с HTTP- и SQL-спанами
и скриншот метрик Grafana после создания и завершения поездок. Укажите `trace_id`
одного запроса и соответствующую запись JSON-лога, чтобы показать корреляцию.
Скриншоты нужно сделать в работающем окружении; шаблон дашборда их не заменяет.

## Тесты

Unit-тесты запускаются без PostgreSQL:

```bash
make test
```

Команда использует `-race -count=2`, сохраняет `coverage.out` и печатает
покрытие. Интеграционные тесты отделены тегом `//go:build integration` и в этот
запуск не входят.

Для интеграционных тестов нужен PostgreSQL из учебного окружения:

```bash
tripgoctl cluster start        # если кластер ещё не запущен
tripgoctl environment start    # поднимает PostgreSQL и создаёт .env
make test-integration
```

Makefile экспортирует переменные из `.env`. Тестам нужны `DATABASE_URL`,
`DATABASE_CONNECT_TIMEOUT` и `DATABASE_QUERY_TIMEOUT`; их можно также передать
через окружение. Без настроек или доступной БД запуск завершается ошибкой,
тесты не пропускаются. Оба набора запускаются с `-race -count=2`.

Каждый тест создаёт отдельную схему `trip_test_<uuid>`, применяет в неё
миграции проекта через Goose и удаляет схему через `t.Cleanup`. Роль из
`DATABASE_URL` должна иметь право `CREATE` в базе. Применять миграции к схеме
приложения перед тестами не нужно; существующие таблицы и данные не изменяются.

Проверяются сохранение всех полей поездки, конфликты водителя и первичного
ключа, отсутствие поездки, история статусов, создание и завершение через
реальные usecase и PostgreSQL. Отдельные проверки подтверждают `FOR UPDATE`,
освобождение блокировки, полный откат двух таблиц, откат при ошибке истории,
отмене контекста и панике, а также переиспользование вложенной транзакции.
Для проверки блокировки используется `NOWAIT`, без `time.Sleep`.
В набор интеграционных тестов также входят проверки OTLP по HTTP/protobuf и
gRPC с локальными приёмниками: реальные SDK отправляют спаны и метрики,
проверяются protobuf-сообщения и пути `/v1/traces`, `/v1/metrics`.

## Команды Makefile

* make generate — генерация Go-кода по контракту OpenAPI и моков через `go generate`.
* make test — unit-тесты с детектором гонок, повторным запуском и отчётом о покрытии.
* make test-integration — интеграционные тесты репозитория, транзакций и OTLP-экспорта с `-race -count=2`.
* make lint — проверка кода через `golangci-lint`.
* make migrate — применение SQL-миграций Goose (up).
* make run — запуск HTTP-сервиса.
